# 감사 절차 Skill

에이전트에게 주는 **추론의 방향성**을 파일 단위로 분리한 것이다. 하나의 Skill은 하나의 감사 절차에 대응한다.

## 왜 프롬프트가 아니라 파일인가

"회계 문제를 찾아줘"라는 지시는 세 가지 방식으로 실패한다.

1. **매번 다른 것을 본다.** 같은 데이터를 두 번 돌리면 다른 발견사항이 나온다. 감사는 재현 가능해야 한다.
2. **기각을 못 한다.** 무엇이 문제인지만 알려주면 에이전트는 모든 것을 문제로 본다. 정상 거래를 정상이라고 판단하는 기준이 함께 있어야 한다.
3. **절차를 설명하지 못한다.** "왜 이걸 봤나"에 답할 수 없으면 조서로 쓸 수 없다.

절차를 파일로 분리하면 버전 관리가 되고, 하나씩 검증할 수 있고, 회사·산업별로 교체할 수 있다. 실무의 감사 프로그램(audit program)이 문서로 존재하는 이유와 같다.

## Skill 구조

모든 Skill은 아래 7개 절을 갖는다.

| 절 | 내용 | 수행 주체 |
|---|---|---|
| 1. 목적 | 이 절차가 무엇을 잡으려 하는가 | — |
| 2. 입력 | 어떤 파일을 어떤 키로 조인하는가 | — |
| 3. 결정론적 계산 | 집계·차이·비율 계산 | **Python** |
| 4. 판단 | 계산 결과를 어떻게 해석하는가 | **LLM** |
| 5. 기각 조건 | 무엇을 문제로 보지 않는가 | **LLM** |
| 6. 근거 요구 | 보고하려면 무엇을 인용해야 하는가 | 검증 단계 |
| 7. 산출 | 조서 항목으로 어떻게 쓰는가 | — |

**3절과 4절의 경계가 이 프로젝트의 핵심 설계다.** 금액·비율·차이는 전부 Python이 계산한다. LLM은 어느 계산을 요청할지 정하고, 나온 숫자를 해석하고, 다른 Skill의 결과와 연결한다. LLM이 산술을 하면 그 조서는 신뢰할 수 없다.

**5절이 없는 Skill은 쓰지 않는다.** 기각 조건 없이 돌리면 정상 거래까지 전부 발견사항으로 올라온다.

## 실행 순서

1~5는 **독립적으로 병렬 실행**한다. 서로의 결과에 의존하지 않는다.

**6은 1~5가 끝난 뒤에 실행한다.** 6은 새로운 데이터를 보는 절차가 아니라 앞선 발견들을 하나의 서사로 엮는 종합 판단이기 때문이다. 개별 발견을 나열하는 데서 끝나면 "정리"이고, 인과로 연결하면 "진단"이다. 그 차이를 만드는 것이 6번이다.

## 위험 등급

| 등급 | 기준 |
|---|---|
| **High** | 재무제표 금액에 직접 영향을 주고, 금액이 세전이익의 5% 이상 |
| **Medium** | 금액 영향이 있으나 5% 미만이거나, 금액 확정에 추가 확인이 필요 |
| **Low** | 금액 영향은 없으나 공시·내부통제 미비에 해당 |
| **관찰사항** | 현재 문제는 아니나 추세가 지속되면 문제가 될 사항 |

세전이익 5%는 실무의 통상적 수행중요성 수준을 따른 것이다. 회사 규모에 따라 조정한다.
