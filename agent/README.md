# 에이전트 오케스트레이션

`skills/`(절차 정의)와 `tools/`(결정론적 계산)를 실제 LLM 루프로 잇는 계층이다.

의존성 없음. Anthropic SDK 대신 `urllib` 로 Messages API 를 직접 호출한다.

```bash
python -m agent.run --dry-run       # 키 없이, 전송할 프롬프트와 도구 스키마 확인
python -m agent.run                 # 6개 절차 전부
python -m agent.run costing         # 하나만
python -m agent.run --out out/      # 조서 JSON 저장
python -m unittest discover tests   # 50개 검증 (API 키 불필요)
```

API 키는 환경변수 `ANTHROPIC_API_KEY` 또는 프로젝트 루트 `.env` 에서 읽는다.
`.env` 는 `.gitignore` 에 있다. 키는 요청 헤더에만 쓰이고 로그·전사기록·예외
메시지 어디에도 남지 않는다.

## 무엇을 LLM 에 맡기고 무엇을 맡기지 않는가

```
skills/*.md  1·2절 ─┐
             3절 ───┼──→ tools/       결정론적 계산. 판단하지 않는다.
             4~7절 ─┴──→ agent/       판단·기각·근거·산출. 계산하지 않는다.
```

이 경계는 프롬프트로 부탁하는 것이 아니라 **도구 스키마로 강제한다.** 에이전트가
쓸 수 있는 도구는 넷뿐이다.

| 도구 | 하는 일 | 왜 이 형태인가 |
|---|---|---|
| `run_procedure` | 3절 계산 실행 | 숫자를 얻는 유일한 통로. 암산할 이유를 없앤다 |
| `lookup_records` | 원천 CSV 행 조회 | 적요 원문을 지어내지 않게. 집계는 안 된다 |
| `emit_finding` | 발견사항 제출 | 근거를 코드가 대조한다. 조서 형식이 스키마다 |
| `emit_rejection` | 후보 기각 기록 | 기각도 결과다. 기록이 없으면 검토 여부를 알 수 없다 |

## 지어낸 근거를 걸러내는 방식

README 4.2("근거 없는 발견은 격하한다")를 코드로 만든 부분이다.

에이전트는 그럴듯한 전표번호를 만들어낼 능력이 충분하다. 그래서 인용을 믿지 않고
[`evidence.py`](evidence.py) 가 원천 CSV 와 대조한다.

| 상태 | 처리 | 근거등급 |
|---|---|---|
| 행이 실재하고 인용문도 그 행에 있음 | 발견사항 | A |
| 행은 실재하나 인용문이 없거나 그 행에 없음 | 발견사항 | B |
| 행이 원천 데이터에 없음 | **미확인 가설로 격하** | C |
| 근거 인용이 아예 없음 | **미확인 가설로 격하** | C |

격하는 LLM 이 아니라 코드가 정한다. 근거 하나라도 대조에 실패하면 그 발견 전체가
격하된다.

**격하 사실은 즉시 에이전트에게 회신한다.** 조용히 격하하면 에이전트는 자기가
무엇을 잘못했는지 모른 채 끝나고, 조서에는 이유 없이 등급이 내려간 항목만 남는다.
회신을 받으면 실재하는 번호로 근거를 교체해 다시 제출할 수 있다.

```
제출됨: 미확인 가설 (근거등급 C)
  기말 단기차입 후 익년 즉시 상환
  [확인 실패] gl_journal.voucher_no=JV202412-9999 — 원천 데이터에 없는 행이다
이 발견은 미확인 가설로 격하되었다. 실재하는 번호로 근거를 교체해 다시 제출할 수
있다. 찾을 수 없다면 격하된 상태로 두라. 지어낸 번호를 붙이는 것보다 낫다.
```

행이 실재하는데 **적요만 지어낸 경우**를 따로 잡는 이유는, 이쪽이 더 위험하기
때문이다. 전표번호가 맞으면 검토자는 인용문까지 대조하지 않는다.

## 절차 하나 = 대화 하나

여섯 절차를 한 대화에 몰아넣지 않는다.

앞 절차의 결론이 뒤 절차의 판단을 오염시킨다. 기간귀속에서 "매출을 당겨
인식했다"고 결론 낸 대화에서 원가 절차를 이어 돌리면, 원가 판단이 그 결론에 맞춰
기울어진다. 독립적으로 판단하게 하고, 엮는 일은 6번 절차에서 명시적으로 한다.

6번(자원배분 정합성)만 예외적으로 앞선 다섯의 **판단 결과**를 입력으로 받는다.
계산 결과가 아니라 판단 결과를 넘기는 것이 핵심이다 — 개별 발견을 나열하면
"정리"이고, 인과로 연결하면 "진단"이다.

계산 결과 자체는 절차 간에 공유한다. 같은 CSV 를 여섯 번 다시 읽을 이유가 없고,
두 번 계산하면 결과가 갈릴 여지가 생긴다.

## 프롬프트의 원본은 skills/*.md 다

[`prompts.py`](prompts.py) 는 절차 본문을 파일에서 읽어 그대로 넣는다. 프롬프트
문자열을 코드에 복사해 두면 `skills/*.md` 를 고쳐도 동작이 안 바뀌는 상태가 되고,
그때부터 문서와 실제가 갈라진다. 테스트가 이것도 검사한다.

`--dry-run` 은 API 호출 없이 전송할 내용 전부를 출력한다. 프롬프트를 보지 않고
결과만 보면, 잘 나온 것이 설계 덕인지 우연인지 알 수 없다.

## 검증

```
python -m unittest discover tests -v      # 50 tests, API 키 불필요
```

LLM 호출은 대본(`FakeClient`)으로 대체한다. 검증 대상은 모델의 답이 아니라
**그 답을 어떻게 받아 처리하는가**다.

| 묶음 | 검증 |
|---|---|
| `TestSkillParsing` | 7개 절 존재, 기각 조건 비어 있지 않음, 본문이 프롬프트에 실제로 들어감 |
| `TestToolSchemas` | required 필드가 properties 에 있음, 기각 검토가 필수임 |
| `TestEvidenceVerification` | 지어낸 전표번호 격하, **지어낸 적요 격하**, 회신 문구에 실패 사유 포함 |
| `TestToolbox` | 계산 결과 재사용, 도구 오류가 대화를 끊지 않음 |
| `TestOrchestration` | 루프 종료, **턴 상한 도달을 완료로 위장하지 않음**, 조서에서 가설 분리 |
| `TestPromptBoundary` | 시스템 프롬프트가 경계를 실제로 말하고 있음 |

`test_run_procedure_result_is_reused` 는 실제로 버그를 잡았다. `precomputed or {}`
가 빈 dict 를 새 dict 로 바꿔서 첫 절차의 계산 결과가 뒤 절차에 전달되지 않았다.

## 한계

- 1~5 절차를 순차 실행한다. 서로 의존하지 않으므로 병렬화할 수 있으나 하지 않았다.
- 재시도는 HTTP 수준만 한다. 모델이 형식을 틀린 경우의 복구는 도구 오류 회신에 의존한다.
- 턴 상한(기본 16)에 걸리면 잘린 결과를 그대로 낸다. `stopped` 필드에 남기고 감춘다.
- 조서 렌더러가 없다. 지금은 JSON 과 콘솔 요약까지다.
- 정답지 기준 채점이 아직 없다. `--out` 이 남기는 `runs.json` 이 그 입력이 된다.
