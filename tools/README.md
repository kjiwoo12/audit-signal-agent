# 결정론적 계산 도구

각 Skill의 **3절(결정론적 계산)** 을 구현한 코드다. Skill 하나에 모듈 하나가 대응한다.

의존성 없음. 표준 라이브러리만 쓴다.

```bash
python -m tools.run                 # 6개 절차 전부 실행, 요약 출력
python -m tools.run costing         # 특정 절차만
python -m tools.run --json          # 에이전트에 넘길 원본 JSON
python -m tools.run --out out/      # 절차별 JSON 파일로 저장
python -m unittest discover tests   # 검증
```

## 왜 이걸 따로 만드는가

LLM에게 CSV를 통째로 주고 "매출채권 증가율을 계산해줘"라고 해도 답은 나온다. 대체로 맞다.

**대체로 맞는 숫자는 감사조서에 쓸 수 없다.** 근거가 약한 가설은 "확인이 필요하다"고 쓰면 되지만, 합계가 틀리면 그 조서는 전부 폐기된다. 그래서 금액·비율·차이는 전부 여기서 계산하고, LLM은 **어느 계산을 요청할지 정하고 나온 숫자를 해석하는** 역할만 맡는다.

```
LLM  : "P-C의 배부기준이 기계시간이 아니라 노무비다. 재배부하면 어떻게 되는지 계산해줘"
Python: costing.analyze() → 활동기준 재배부, 합계 검증, 정확한 금액 반환
LLM  : "P-C가 31.8% 흑자에서 8.2% 적자로 뒤집힌다. 이것이 의미하는 바는..."
```

## 설계 규칙

### 1. 판단하지 않는다

출력에 `발견사항`·`위험등급`·`결론` 같은 키는 없다. 없어야 한다.

이 경계는 문서로만 지켜지지 않아서 [테스트로 강제](../tests/test_tools.py)한다. `TestPythonLLMBoundary`가 모든 절차의 출력 키를 순회하며 판단성 키가 섞여 들어왔는지 검사한다.

같은 이유로 이 도구는 `return_reasons`를 **원문 그대로** 넘긴다. `"규격불량 반품"`과 `"미판매 재고 반품"`을 "반품"으로 합치는 순간, 정상 품질반품과 위탁판매를 가르는 유일한 신호가 사라진다. 코드가 요약하면 안 되는 것이 있다.

### 2. 조회 범위와 판정 기준을 구분한다

`window_biz_days=10` 같은 인자는 **어디까지 볼 것인가**이지 **무엇이 문제인가**가 아니다. 무엇을 보고하고 무엇을 기각할지는 Skill 4·5절이 정한다.

이 구분이 무너지면 임계값이 코드에 숨고, 왜 그 건이 걸렸는지 설명할 수 없게 된다.

### 3. 없는 것은 없다고 말한다

`divergence.analyze()`는 채권 연령의 전기 대비 변화를 계산하지 않고 `unavailable`에 이유와 함께 남긴다. 전기 연령 자료가 데이터셋에 없기 때문이다.

`coherence.analyze()`는 적요에 제품 식별자가 없는 설비대금 지급을 `unidentified`로 남긴다. 비례배분으로 추정하지 않는다. 식별된 투입액이 0인 제품에는 순위를 매기지 않는다 — 0원끼리 순위를 매기면 존재하지 않는 정합성 불일치가 만들어진다.

### 4. 반증자료를 함께 낸다

각 절차는 `counter_facts`를 함께 반환한다. Skill 5절의 기각 조건은 근거가 있어야 적용되기 때문이다.

| 절차 | 반증자료 | 없으면 생기는 오탐 |
|---|---|---|
| 기간귀속 | 12월 매출 배수, 선출고 후 송장 건수 | 계절적 매출 급증을 조기인식으로 본다 |
| 거래의 실질 | 전체 평균 반품률, 평균 이하 거래처 목록 | 모든 반품을 위탁판매로 본다 |
| 기말 이례거래 | 보고기간 중간 차입 6건 | 모든 단기차입을 외형 보정으로 본다 |

### 5. 합계가 어긋나면 멈춘다

`costing.py`는 활동 풀 합계가 간접비 총액과 다르면 `ArithmeticError`를 던지고 중단한다. 동인 사용량 합계가 `driver_total`과 다를 때도 마찬가지다.

배부는 `split_exact()`로 하고, 최대잔여법으로 잔차를 배정해 합계를 원 단위까지 맞춘다. 반올림 오차 몇 원이 남은 배부표는 조서에 쓸 수 없다.

## 검증

```
python -m unittest discover tests -v      # 27 tests
```

| 묶음 | 검증 |
|---|---|
| `TestDatasetTieOut` | GL 차변=대변, 판매시스템 매출=GL 매출계정, 송장-출고 대응 |
| `TestArithmetic` | 배분 합계 보존, 영업일 계산 |
| `TestCosting` | 재배부 합계 일치, **배부기준을 바꿔도 총 매출총이익 불변** |
| `TestCutoff` | 후보가 실제로 기간을 넘는지, 통제이전일이 인도조건을 따르는지 |
| `TestSubstance` | 특수관계자 오매칭 회귀, 반품 사유 원문 보존 |
| `TestWindow` | 거래쌍의 금액·방향, 이자 지급 혼입 회귀 |
| `TestPythonLLMBoundary` | 판단성 키 부재, JSON 직렬화, Skill 파일 존재 |

회귀 테스트 두 개는 실제로 잡은 버그다.

- 거래처명 부분일치가 너무 느슨해 **13개 거래처 전부가 특수관계자로 매칭**되던 오류. 괄호 안을 먼저 제거하고 핵심 토큰끼리 비교하도록 고쳤다.
- 적요에 `"차입"`이 들어간 건을 모두 세어 이자 지급까지 기중 차입으로 잡던 오류. 반증자료의 건수가 6건이 아니라 17건으로 나왔다.

둘 다 에이전트에 잘못된 사실을 먹였을 것이고, 그 위에서 나온 판단은 검토 단계에서 걸러지지 않는다.

## 한계

- 영업일 계산에 공휴일 달력이 없다. 주말만 제외한다.
- 대응 매출원가는 전부원가율 근사다. 변동원가만 되돌리면 영향금액이 달라진다.
- 원가 배부는 연 1회 단일 배부다. 월별 배부율 변동은 반영하지 않았다.
- 제품별 자원 귀속은 적요 문자열에 의존한다. 실무에서는 프로젝트 코드나 자산 대장을 써야 한다.
